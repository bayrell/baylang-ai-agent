# Code Review проекта BayLang AI

Дата ревью: 2026-02-11. Изучены: `src/` (Python-клиент), `server/` (PHP + SQLite),
`Dockerfile`, `build.sh`, `requirements.txt`, `README.md`, `docs/`.

## Обзор

Проект — система foreground-выполнения задач: PHP-сервер с SQLite раздаёт задачи
агентам, Python-клиент опрашивает сервер раз в `POLL_INTERVAL` секунд и выполняет
задачи через AI (pydantic-ai + OpenRouter), коммитит и пушит результат, затем
отчитывается серверу. Есть AJAX веб-интерфейс и Docker-контейнер клиента.

Архитектура **понятная и минимальной достаточности**: сервер — один самодостаточный
`api.php` без фреймворков, клиент — три модуля (`main.py` → `foreground.py` → `app.py`).
Логика разделена аккуратно, лишнего кода нет.

## Что нравится (сильные стороны)

- **Атомарный захват задачи**: `task_start` делает `UPDATE ... WHERE status='planned'`
  и возвращает `ok` по `rowCount()` — гонка между двумя воркерами исключена на уровне
  БД, а не кода. Это правильный подход.
- **Параметризованный SQL** во всех запросах `api.php` — SQL-инъекций нет, фильтры
  UI собираются через плейсхолдеры `?`.
- **XSS-защита в интерфейсе**: `server/main.js` экранирует всё через `esc()`, включая
  данные из БД (имена задач, ошибки).
- **Прагматичные мелочи**: ротация логов `RotatingFileHandler`, дублирование в stdout
  для Docker, защита от `POLL_INTERVAL=0` (tight-loop), миграция `PRAGMA table_info`
  для добавления `projects.branch`, WAL-режим SQLite, переопределение конфига через
  env с сохранением обратно в `config.json`.
- **Решение с датой коммита** (`get_commit_date` + ожидание перед push) продуманно
  документировано и аккуратно откатывается, если команда недоступна.
- Документация **синхронизирована с кодом** в основном: README, AGENTS.md и
  `docs/foreground.md` описывают реальный workflow.

## Возможные баги

### Критичные

1. **`run_git` без таймаута и без отключения промптов git** (`src/foreground.py:148`).
   `subprocess.run` вызывается без `timeout` — если `git pull`/`push` виснет на сети
   или git запрашивает креды (HTTPS-пароль, SSH-фразу), **foreground зависает навсегда**
   без единой записи в лог. Нужно: `timeout=` в `subprocess.run` и env
   `GIT_TERMINAL_PROMPT=0` (плюс `GIT_SSH_COMMAND=BatchMode=yes`).

2. **Задача навсегда зависает в статусе `running`**. Если клиент упал/перезапустился
   в середине задачи (kill контейнер, обрыв посреди AI-вызова), статус останется
   `running` навсегда: `plan` выбирает только `planned`, таймаута и requeue нет.
   Нужен либо recovery (возвращать `running` в `planned` после N секунд), либо
   heartbeat.

3. **`push` новой ветки упадёт без upstream** (`src/foreground.py:288`).
   Если `checkout -B branch` создал ветку локально, `git push` вернёт
   «no upstream branch» → `GitError` → задача уйдёт в `error`, хотя работа сделана.
   Нужен `git push -u origin <branch>`.

4. **Грязное дерево переносится между задачами** (`src/foreground.py:256-263`).
   `git pull` идёт *до* checkout, а при ошибке checkout делается принудительный
   `checkout -B`. Если предыдущая задача упала, оставив изменения в дереве, они
   **вложатся в коммит следующей задачи** (ведь `git add -A`), — кросс-контаминация
   задач. Плюс `pull` идёт не на целевой ветке, то есть ветка задачи обновляется
   не всегда. Логичнее: `fetch` → `checkout` → `pull --ff-only` на целевой ветке,
   а перед этим чистка/reset при грязном дереве.

### Средние

5. **`git commit` падает, если менять нечего** — после повторного/повторяющегося
   задания `docs/task.md` может не измениться, `git commit` вернёт ненулевой код →
   `GitError` → ложная ошибка задачи. Нужно либо проверять `git status --porcelain`,
   либо tolerate пустой коммит.

6. **Падение на пустом репозитории**: `git log -1 --format=%ct` (`foreground.py:279`)
   бросает `GitError`, если коммитов ещё нет (свежий клон без истории — крайний случай,
   но возможен). Также `int(prev_ts)` не защищён от мусора.

7. **Путаница при ошибке отправки результата** (`foreground.py:327-334`):
   если `task_done` упал по сети (таймаут), код ловит это как «ошибку задачи» и шлёт
   `task_error` — **успешно выполненная и запушенная задача пометится error** (если
   `task_error` пройдёт) или зависнет в `running` (если не пройдёт). Стоит разделять
   ошибки выполнения и ошибки коммуникации с сервером.

8. **Скорость обработки: 1 задача за цикл опроса.** После успешной задачи клиент
   делает `break` и спит полный `POLL_INTERVAL` (5 минут), даже если на сервере ждут
   ещё десятки задач. Для очереди это существенно: лучше сразу перечитывать `plan`,
   а спать только когда задач нет.

9. **Некорректный `BAYLANG_PROJECTS`/`config.json` роняет клиент на старте**:
   `parse_projects` при JSON-ошибке бросает `json.JSONDecodeError`, а `load_config`
   при битом `config.json` — тоже; исключение не перехватывается → foreground не
   стартует без понятного сообщения.

10. **`task_save` позволяет менять статус произвольно** — можно перевести
    `running`-задачу обратно в `planned` (или в `done`), пока агент её делает:
    задача начнётся второй раз параллельно. Стоит запрещать смену статуса на
    редактировании или ограничивать переходы.

### Мелкие / к улучшению

11. **Документация расходится с кодом**: `docs/foreground.md:58` упоминает env
    `BAYLANG_PROJECTS_DIR` (папка с проектами) — **такой переменной в коде нет**
    (есть только `BAYLANG_PROJECTS`). Либо реализовать, либо убрать из доков.

12. **`requirements.txt` без версий** (`pydantic-ai`, `httpx` и т.д.) — сборка
    Docker-образа не воспроизводима: обновление зависимости сломает прод завтра же.
    Нужен пиннинг (`pip freeze` или диапазоны).

13. **Секьюрити**: пароли basic auth захардкожены в `server/config.php`
    (`admin`/`admin`), дефолтный пароль дублируется в `DEFAULT_CONFIG` клиента и
    пишется в `config.json` открытым текстом. По отсутствию `X-Frame-Options`,
    `Strict-Transport-Security` и т.п. — приемлемо для внутреннего инструмента,
    но для публичного размещения надо выносить креды в env и добавлять заголовки.

14. **`api.php` отдаёт текст исключения PDO** клиенту — раскрывает пути/структуру
    БД (информация для атакующего с кредами). Логировать на сервер, клиенту —
    общее сообщение.

15. **SQLite «database is locked»**: WAL включён, но `busy_timeout` не задан —
    при одновременных запросах UI и агента возможны кратковременные
    `PDOexception`. Достаточно `PRAGMA busy_timeout=5000`.

16. **История задач не сохраняется**: в `process_task` создаётся `AI`, но `ai.save()`
    не вызывается — в `~/.baylang/history/` не попадает ничего от foreground, только
    от интерактивного режима. Если персистентность задумывалась для диагностики —
    стоит добавить.

17. **`AI.id = str(int(time.time()))`** (`app.py:112`) — два экземпляра в одну
    секунду получат одинаковое имя файла истории и затрут друг друга. Мелочь, но
    `uuid4` дешевле.

18. **`httpx.AsyncClient` никогда не закрывается** (`ServerClient`) — для
    долгоживущего демона не страшно, но при остановке стоило бы `aclose()`
    (и ловить `httpx.HTTPStatusError` отдельно: сейчас 401/500 сервера
    вываливаются в общий `except` цикла как «Ошибка цикла foreground»).

19. **Нет лимита на `GET plan`** — сервер возвращает все planned-задачи разом;
    при большой очереди это O(n) памяти на каждый опрос. `LIMIT` не помешает.

20. **`fillSelect` в `main.js`** при пустом списке проектов/агентов оставляет
    `<select>` без опций — форма задачи отправится с пустым `project_id`
    (валидация `required` спасёт, но UX стоило бы улучшить подсказкой).

## Рекомендации (приоритетный список)

1. Добавить таймауты в `run_git` и отключить git-промпты — устраняет зависания.
2. Сделать recovery задач в статусе `running` (requeue по таймауту).
3. `git push -u origin <branch>` + чистка/проверка дерева перед работой.
4. Разделить ошибки выполнения задачи и ошибки коммуникации с сервером.
5. Спать только тогда, когда задач нет — обрабатывать очередь быстрее.
6. Запиннить зависимости в `requirements.txt`.
7. Убрать/реализовать `BAYLANG_PROJECTS_DIR` в `docs/foreground.md`.

## Итог

Проект **в целоро хорошо сделан**: атомарный захват задач, чистый SQL, экранирование
в UI, аккуратная документация и продуманные детали вроде ожидания даты коммита.
Критичных архитектурных ошибок нет, но есть **четыре реальных бага эксплуатации**:
отсутствие таймаутов у git-команд (вечное зависание), отсутствие recovery для
`running`-задач, падение `push` для новых веток и перетаскивание грязных изменений
между задачами. Их стоит починить в первую очередь — всё остальное (пиннинг
зависимостей, мелкие UX и секьюрити-улучшения) идёт следующей волной.
